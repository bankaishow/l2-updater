# Аудит безопасности апдейтера (2026-10-29)

Объём: `src/L2Updater.Core` (подпись, разбор, пути, скачивание, самообновление, запуск игры и защитной программы), окно `L2Updater.App` (сеть, запуск, настройки), `.github/workflows/build.yml`, `tools/updater_build.py`, порядок выпуска (`docs/release.md`). Версия кода: коммит `6b54ea0` (сборка 0.1.25). Метод: чтение кода, тестов не писал и не запускал; на этой машине нет `dotnet`.

Модель угроз из `docs/plan.md`: сайт или хранилище файлов взломаны, но закрытого ключа подписи у злоумышленника нет. Игрок не должен получить чужой файл.

## Что сделано правильно

- Подпись проверяется раньше разбора и на точных байтах документа. Ключ выбирается из списка доверенных по `key_id`, подпись строго 64 байта (IEEE P1363), любая ошибка = отказ без исключения. Битый доверенный ключ отклоняется при старте.
- Откат манифеста: `serial` не может быть меньше уже принятого. Явный `null` и неизвестная форма полей отклоняются.
- Пути (`PathGuard`): нет `..`, абсолютных путей, `:` (диски и альтернативные потоки), обратных слэшей, зарезервированных имён Windows, точки или пробела в конце; проверка «внутри папки игры» с разделителем после корня; предел длины. Проверяются и пути удаления, причём все до первого удаления.
- Скачивание: только `https`, каждый файл проверяется по точному размеру и SHA-256 до замены, недокачанный файл не подменяет готовый, лимиты 16 МБ (документы) и 300 МБ (апдейтер). .NET не пускает перенаправление с https на http.
- Самообновление: файл проверяется по размеру и SHA-256 из подписанного манифеста, замена с откатом, защита от зацикливания флагом `--updated`.
- Нет отключения проверки сертификатов, нет секретов в репозитории и в CI (права `contents: read`, запись только у задачи публикации), ключа подписи в репозитории нет.
- Защитная программа (`guard`): путь из подписанного манифеста и проверяется как все пути, запуск без оболочки и без окна, таймаут с убийством процесса, вывод не разбирается и не показывается.

## Находки

### 1. Нет защиты от отката и «заморозки» `files.json` (средняя, проект формата)
Манифест защищён номером `serial`, а `files.json` нет: он подписан, но не привязан к манифесту. Взломанный сайт или хранилище может отдать **старый, ранее выпущенный** `files.json` с настоящей подписью (в R2 старые файлы по правилам выпуска остаются). Игроки получат прежнюю версию клиента, в том числе с уже исправленной уязвимостью, и не заметят этого. То же с заморозкой: отдавать устаревший манифест, пока его `serial` не ниже принятого.
Предложение: в запись клиента в манифесте добавить `files_sha256` (хеш `files.json`), апдейтер сверяет его после загрузки; манифест уже защищён от отката. Для заморозки добавить в манифест `expires_at` и отказывать после него. Изменения: `ManifestParser`, `UpdateSession.LoadFileListAsync`, `updater_build.py` (сначала `files`, потом `manifest`, как уже и делается), `docs/format.md`, тесты.

### 2. Закрытый ключ подписи лежит на диске без пароля (средняя, эксплуатация)
`updater_build.py` читает ключ с `password=None`, `release.pem` на Windows-машине разработки хранится открытым текстом, рядом с игровыми клиентами, скачанными архивами и инструментами. Заражение этой машины = возможность подписать что угодно, а отозвать ключ можно только пересборкой апдейтера (и игроки со старой версией не получат её сами, если подписано чужим ключом).
Предложение: ключ под паролем (добавить `--password` или запрос через `getpass`, шифрование PEM `BestAvailableEncryption`) или хранить на аппаратном токене; копию ключа зашифровать; отдельный пользователь Windows или отдельная машина для подписи; заранее выпустить второй ключ и держать его запечатанным (`TrustedKeys` уже поддерживает несколько ключей, так что ротация возможна без потери игроков).

### 3. Цепочка выпуска апдейтера и сборка (низкая–средняя)
- Для игроков exe пока лежит в релизе `test-build` (предрелиз, текст «Test signing key, not for players» **уже неверен**: с 2026-10-26 в сборке боевой ключ). Релиз пересоздаётся каждым пушем, значит ссылка нестабильна, а любой пуш в `main` меняет то, что скачивает новый игрок.
- Действия GitHub (`actions/checkout@v4` и др.) закреплены по тегу, а не по хешу коммита.
- Для новых игроков корень доверия при первом скачивании — аккаунт GitHub (SmartScreen и хеш не защищают). Для уже установленных апдейтеров самообновление защищено подписанным манифестом.
Предложение: отдельный workflow выпуска по тегу (`v0.1.x`) с защищёнными ветками/тегами и включённой двухфакторной защитой аккаунта; закрепить действия по хешу; поправить текст релиза; отдавать игрокам файл с `dl.dimythras.com` и публиковать SHA-256 рядом со ссылкой на сайте. SignPath Foundation всё равно потребует воспроизводимую сборку в GitHub Actions из тегов.

### 4. Служебная папка `.l2updater/` не закрыта для путей из списка (низкая) — ИСПРАВЛЕНО 2026-10-29
`files.json` может положить файл в `.l2updater/cache.json` или `.l2updater/tmp/`. Список подписан владельцем, так что это защита от собственной ошибки, но подмена кэша хешей скроет изменённые файлы от обычной проверки.
Исправлено в `ManifestParser` (не в `PathGuard`: самому апдейтеру путь `.l2updater/cache.json` нужен): `files` и `delete` с первым сегментом `.l2updater` (без учёта регистра) отклоняются, тесты `ManifestServiceFolderTests`. Остаточный риск: короткое имя 8.3 этой папки на NTFS; список подписан владельцем, считаем приемлемым.

### 5. Ссылки и перенаправления внутри папки игры (низкая)
`PathGuard` проверяет путь лексически (`GetFullPath`). Если внутри папки игры есть junction или символическая ссылка (создана вручную или программой), запись пойдёт за её пределы. Заметно только когда апдейтер запущен с повышенными правами, например игра в `Program Files`; апдейтер лишь предупреждает об этом, но продолжает.
Предложение: не писать и не удалять файл, если у одной из существующих родительских папок до корня атрибут `ReparsePoint`; при установке в защищённую папку не продолжать, а просить выбрать другую.

### 6. Кэш хешей верит размеру и времени файла (информационная)
Обычная проверка пропускает файл, если размер и время изменения совпали с записью кэша. Вредоносная программа, которая может писать в папку игры, может сохранить время изменения и подменить содержимое. Кнопка «Проверить все файлы» кэш игнорирует. Это не граница безопасности (программа с правом записи в папку игры обходит апдейтер и так), оставить как есть, но не обещать игрокам «целостность клиента».

### 7. Файл `guard` проверяется только при обновлении (информационная)
Перед запуском игры апдейтер не сверяет хеш защитной программы с `files.json`: тот, кто может подменить файл в папке игры, получит выполнение кода при нажатии «Играть». Такая же возможность у `l2.exe`, и это модель угроз проекта анти-чита (защиту обходит владелец компьютера, сервер решает по подтверждению). Если хочется закрыть: перед запуском считать SHA-256 файла (маленького) и сверять с последним `files.json` (его придётся хранить рядом с кэшем).

### 8. Операционные риски выпуска (информационная, добавить в `release.md`)
- `serial` манифеста берётся из часов машины, которая подписывает. Манифест с ошибочно большим `serial` блокирует все дальнейшие манифесты у тех, кто его принял; выход только новым ключом. Перед подписью проверять дату на машине.
- Потеря `release.pem` = невозможность выпускать обновления. Хранить зашифрованные копии (см. находку 2).
- Игроки со старыми версиями апдейтера не знают про новые поля манифеста (`guard`, будущие `files_sha256`): они их игнорируют, и защита у них не работает. Поэтому новые защитные поля вводятся только вместе с обязательным обновлением апдейтера (повышение версии в манифесте).
